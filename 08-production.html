Part 8 · Running an LLM feature for real users

What changes when real users start depending on my AI feature?

This guide takes your working prototype and turns it into something that runs thousands of times a day without surprises. By the end you will be able to estimate the speed and cost of a feature before you ship it, keep it up when the model provider is down, see exactly what happened in any conversation, and change prompts and models without breaking what already works.

Step 0 · The gap

From demo to product

A demo has to work once, for you. A product has to work thousands of times a day, for strangers. This chapter names the five things that change.

By now you can build something that works: a prompt (Part 2), maybe some retrieved documents (Part 3) or tools (Part 4), an eval set (Part 5) and safety rules (Part 7). You type a question, the model answers, it looks great. That is a demo.

A product is different in kind, not just in size. Real users type things you never imagined, at three in the morning, on slow phones, while the model provider is having a bad day. They do not tell you when it breaks. They just leave. So a product must be fast, cheap enough to keep running, hard to break, and it must tell you when something goes wrong.

Analogy

Cooking dinner for a friend is a demo. If the sauce splits you laugh and order pizza. Running a restaurant is a product: two hundred covers a night, every plate out in twelve minutes, ingredients paid for, someone noticing when the fridge dies, and no menu changes without telling the kitchen. Same cooking skill, completely different job.

The five concerns of this guide

1Reliability

It keeps working when the model is slow, the answer is malformed, or a provider goes down.

2Speed

The user sees something quickly. Eight seconds of blank screen feels broken even if the answer is perfect.

3Cost

You pay per token. A feature that costs more than it earns gets switched off, however clever it is.

4Observability

You can see inside every call, so you can debug yesterday's complaint and spot problems before users do.

5Change management

You can change a prompt or swap a model without breaking what works, and undo it if you did.

Demo versus product, side by side

Demo

  • Works when you try it
  • One user at a time
  • Cost is a rounding error
  • If it fails, you see it and fix it
  • You edit the prompt in place
  • Test data is your own questions

Product

  • Works thousands of times a day, measured
  • Many users at once, so rate limits and queues matter
  • Cost is tracked per request and per month
  • If it fails, an alert fires and the user still gets something useful
  • Prompts are versioned, tested and rolled out gradually
  • Test data comes from real traffic, with personal data removed
Key idea

Nothing in this guide makes the model smarter. Every technique is about the system around the model: how you call it, catch its failures, watch it, and change it safely. The model is one ingredient. The product is the whole kitchen.

Common doubt

"My prototype works great. Why can't I just ship it?" You can, to a handful of friendly users. The problems here arrive with scale: the first outage, the first surprising bill, the first complaint you cannot reproduce. This guide is so you recognise each one when it comes.

Step 1 · The plumbing

Talking to a model API

What travels over the wire when your app asks a model a question, and the four rules that keep that conversation from breaking.

Your app does not contain the model. It sends a message over the internet to a computer that does. The agreed way for one program to ask another for something is an API (application programming interface). The address you send to is an endpoint. What you send is a request; what comes back is a response.

A request to a chat model is mostly a messages list: the conversation so far, each message labelled with who said it. A system message holds your instructions, then user and assistant messages alternate. You also send settings, most importantly max tokens, the longest answer you will accept.

systemYou are the support assistant for a recipe app. Be brief. If unsure, say so.
userCan I freeze the lemon tart?
assistant (earlier turn)Yes, up to a month. Wrap it well and thaw in the fridge overnight.
user (new)And the pastry cream one?

The whole history goes with every request; the model remembers nothing between calls. This matters for cost (Step 3).

Tokens in, tokens out

The model reads and writes in tokens, chunks of roughly a word or part of a word (Part 1). Everything you send is input tokens; everything the model writes is output tokens. The response reports both. Log them every time; cost and speed depend on them.

Streaming: getting words as they are made

The model produces one token at a time. Normally you wait for the last token, then receive the whole answer. With streaming, the provider sends each token the moment it exists and your app shows it. The total time is the same; the felt time is completely different, because the user sees the first word almost immediately.

One request goes out (orange). Tokens come back one by one (green) and appear in the app as they land. The loop repeats every six seconds.

Four rules that keep the plumbing working

Timeouts

A timeout is the longest you will wait before giving up. Without one, a stuck request can hang your app forever.

Rate limits

Providers cap how much you may send: so many requests per minute and tokens per minute. Go over and you get a "slow down" error instead of an answer.

Retries with backoff

Many failures are temporary. A retry tries again, only for temporary errors and only a few times. Exponential backoff waits longer each time (1 s, 2 s, 4 s). Jitter adds a random extra wait so a thousand clients do not retry in the same instant.

Idempotency

An operation is idempotent if doing it twice has the same effect as once. Asking a question is; "send the refund" is not. Only retry what is safe to repeat, or give each action a unique id so a second attempt is ignored.

Analogy

A non-streaming call is a letter: one day a full reply lands on the mat. A streaming call is a phone call: the other person starts talking straight away. Backoff with jitter is a polite crowd at a busy counter: if everyone rushes back at once nobody gets served; if each waits a slightly different, growing amount of time, the queue clears.

Key idea

Every model call can be slow, fail, or be refused for going too fast. Treat that as normal. A timeout, a capped retry with backoff and jitter, and a clear rule about what is safe to retry are the minimum for every call you ship.

Common doubt

"Should I always stream?" Stream whenever a human is watching the answer appear. Skip it when the output goes to a program (a classifier, a JSON extractor); nothing can use half a JSON object. Streaming also makes error handling harder (Step 4), so it is a choice, not a default.

Step 2 · Speed

Latency: why the model feels slow, and what to do

Two numbers describe how long a call takes. Once you know which one your users feel, most speed fixes become obvious.

Latency is how long you wait for something. A model call has two latencies that matter:

  • Time to first token (TTFT): from sending the request to receiving the first token. This is the blank-screen wait. It grows with input size, because the model must read the whole prompt before writing anything.
  • Total time: until the last token arrives. Dominated by the number of output tokens, because each one needs a full pass through the model.

A related word is throughput: work done per second overall (tokens per second for one stream, requests per second for the whole system). Latency is one user's wait; throughput is how many users you can serve.

The same prompt with a long and a short answer. The wait before the first word is identical; the total is very different.

Analogy

Time to first token is how long until the bread arrives. Total time is how long until the main course is finished. A restaurant that brings bread quickly feels fast even when the kitchen is slow, which is exactly what streaming does for a chat app.

What you can actually do about it

Stream

Does not change total time, but turns a blank wait into visible progress. Do this first.

Ask for shorter answers

Output tokens are the expensive part of the clock. "Answer in two sentences" can halve total time.

Shorten the prompt

Trim the system prompt, send fewer retrieved documents, cut old turns. Helps time to first token and cost.

Use a smaller model for easy cases

Small models write tokens faster. Route simple requests to them (Step 7).

Run independent calls in parallel

If you need a summary and a title, ask for both at once, not one after the other.

Cache

A cached answer takes milliseconds. A cached prompt prefix cuts time to first token (Step 3).

Playground

Latency estimator

A simple model of one call: fixed overhead, then reading the input, then writing the output. Try halving the output tokens, then halving the prompt.

This is an estimate with made-up default speeds. Real values differ by model, provider, region and time of day. Measure your own time to first token and tokens per second, then type them in.

Key idea

Users feel time to first token; your budget feels total tokens. Stream to fix the first, shorten the output to fix the second. Everything else is a smaller lever.

Common doubt

"Is the model slow, or is my app slow?" Measure both. Record when the user clicked, when you sent the request, when the first token landed and when the last one did. If the gap before you even send is large, the problem is your own code (a slow database lookup, a retrieval step) and no model change will help.

Go deeper: why you should measure at the 95th percentile

Line up today's response times from fastest to slowest. The p50 (50th percentile, the median) is the one in the middle; the p95 is the one that 95% of requests beat. Averages hide problems: a mostly-fast system with a few ten-second stalls has a fine average and a terrible p95, and users remember the stalls. Set speed goals on p95.

Step 3 · Money

Cost and caching

Where the money goes in a model call, how to estimate a monthly bill before you get one, and the three kinds of caching that shrink it.

How you are charged

Hosted providers charge per token, usually quoted per million tokens. Input and output have different prices, and output is normally the more expensive. Three consequences follow:

  • Long system prompts cost money on every call. A 2,000-token instruction block is re-sent every time.
  • Conversation history grows. Turn ten re-sends turns one to nine, so long chats get dearer per message.
  • Short answers are cheaper as well as faster. The same lever as Step 2.

Many providers also discount input tokens they processed recently (prompt caching, below). The cost per request is the number to know by heart: it turns "is this affordable?" into arithmetic.

Three kinds of caching

A cache keeps the result of expensive work so you can reuse it. A cache hit is when the thing you need is already there. Three caches matter here, and they solve different problems.

Prompt caching

The provider keeps its processed reading of the beginning of your prompt. If the next request starts with exactly the same text, that part is not re-read: cheaper, and the first token arrives sooner. Helps when a long, stable prefix is followed by a small changing part.

Response caching

Your app remembers the exact answer to the exact input. Same input, same output, no model call. Helps for repeated identical requests, like summarising a product page thousands of people view. Useless for open chat.

Semantic caching

A semantic cache reuses an answer for a question that means the same as one it has seen ("how do I reset my password" and "password reset?"), judged with embeddings (Part 3). Big savings, real risk: similar-looking questions can need different answers.

Prompt caching only helps the part of the prompt that is identical to a recent request, and only from the start. Order your prompt to make that part as long as possible.

Analogy

Prompt caching is a barista who remembers your regular order: you only say "decaf today", and the coffee comes faster. Response caching is a vending machine: same button, same snack, no barista. Semantic caching is a barista who guesses "the usual?" when you mumble. Usually right. Occasionally the wrong drink.

Key idea

Cost is (input tokens × input price) + (output tokens × output price), times requests. You control all of those numbers. Shorter prompts, shorter answers, a cache in front of repeated work, and a smaller model for easy cases are the four dials.

Watch out

Never let a cached answer outlive the facts it depends on. If the price list changes and your response cache still holds yesterday's answer, the model looks wrong when it was your cache. Give every entry an expiry, and clear the cache when the prompt or the source documents change.

Common doubt

"Does prompt caching change the answer?" No. The provider stores its reading of the prefix, not an answer, so the output is the same as if the prefix were processed fresh. Only response and semantic caches return stored answers, and they are the ones that can go stale.

Step 4 · Toughness

Reliability: staying up when the model does not

Providers have outages. Models return garbage. Streams cut out halfway. Here is how a product survives all three without the user seeing a stack trace.

Reliability is not "it never fails". It is "when something fails, the user still gets something reasonable, and the failure does not spread". Six patterns do most of the work.

The orange dot is one request. It enters Model A, which times out, so it drops to Model B, which answers. The user never sees the failure.

Fallback

A fallback is a second option used when the first fails: another model, another provider, or an older prompt. Evaluate it too (Part 5); an untested fallback is just a second way to fail.

Circuit breaker

A circuit breaker notices repeated failures and stops calling the broken thing for a while instead of hammering it with retries. After a cooling-off period it lets one request through to test for recovery.

Graceful degradation

Graceful degradation means a simpler but useful result instead of an error: a cached answer, a link to the help page, or "I can't do that right now, here is a human".

Validate structured outputs

When you ask for JSON, parse it and check the fields. If it is broken, try a repair (a missing bracket); if that fails, retry once with the error message in the prompt.

Guard partial streams

A stream can stop mid-sentence. Track whether it ended cleanly. If not, say the answer was cut off and offer a retry, rather than silently showing half an answer.

Set max tokens

Without a limit, a confused model can write for minutes and charge you for it. Set a ceiling that fits the task, and detect when an answer hit it.

Analogy

A circuit breaker in your house does not keep pushing power into a short circuit until the wiring melts. It trips, waits, and is reset once the fault is fixed. The software version resets itself after a pause and checks whether the fault is gone.

The pattern in code

The whole idea in a few lines of Python. Replace call_model with any provider's client.

# robust_call.py: timeout, retries with backoff, fallback, graceful message
import random, time

class TransientError(Exception):
    # raised for rate limits, timeouts and server errors: worth retrying
    pass

def call_model(prompt: str, model: str, timeout_s: float) -> str:
    # Put any LLM API call here. Raise TransientError on a temporary failure.
    ...

def call_with_retries(prompt: str, model: str, tries: int = 3) -> str:
    for attempt in range(tries):
        try:
            return call_model(prompt, model, timeout_s=20)   # never wait forever
        except TransientError:
            if attempt == tries - 1:
                raise                                        # out of attempts
            wait = 2 ** attempt + random.uniform(0, 1)       # backoff + jitter
            time.sleep(wait)

def answer(prompt: str) -> str:
    try:
        return call_with_retries(prompt, model="primary")
    except TransientError:
        try:
            return call_with_retries(prompt, model="fallback", tries=2)
        except TransientError:
            # graceful degradation: a useful message beats a stack trace
            return "Sorry, I am having trouble right now. Please try again in a minute."
Key idea

Design for the failure, not the happy path. Every call needs an answer to three questions: how long will I wait, what do I do if it fails, and how do I check the output is usable. Write them down before launch.

Common doubt

"If I retry and fall back, won't a bad day cost me double?" Yes, and that is the right trade. A failed request costs you a user; a retried one costs a few tokens. Cap the attempts, use the circuit breaker so an outage does not become a retry storm, and watch the retry rate (Step 5).

Step 5 · Seeing inside

Observability: knowing what happened

A user says "the bot told me something weird yesterday". Can you find that conversation, see the exact prompt, and tell what went wrong? If not, this chapter fixes that.

Observability is being able to understand what your system did from the records it left behind. The record you want is a trace: the complete story of one request, from the user's message to the final answer, including every model call, tool call and retrieval step. Each step is a span: a named piece of work with a start time, an end time and details. Spans nest, which is what makes a trace readable.

Each bar is a span. Nesting shows that the tool call happened inside the planning step. One glance tells you where the two seconds went.

What to log on every call

Logging means writing these records somewhere you can search. For each model call, record:

  • The prompt version and model name, so you know which configuration produced the answer.
  • The inputs and outputs, with personal data redacted.
  • Tokens in and out, latency (first token and total), and the computed cost.
  • Tool calls and their results, and any retrieved documents.
  • Errors, retries and fallbacks, so you can see how often the safety net was used.
  • User feedback once it arrives (a thumbs up, a retry, an escalation).

Dashboards and alerts

A dashboard is a page of charts built from those records: latency at p50 and p95, error and fallback rate, requests per minute against your rate limit, cost per day, and a feedback score. An alert is a rule that pages a person when a chart crosses a line: "p95 above ten seconds for five minutes" or "cost today already above the daily average". Alerts turn a dashboard nobody looks at into a system that looks after itself.

Analogy

A trace is the ticket that follows an order through a restaurant kitchen: who took it, when the starter went out, which station was slow. The dashboard is the board showing how many tickets are open and how long the oldest has waited. The alert is the bell that rings when a ticket has waited too long. You need all three.

Three habits that keep logs useful and safe

Sample for review

You cannot read every trace. Read a random sample every day (say 20), plus every trace with a thumbs-down. This finds problems your metrics do not know how to measure.

Redact personal data

PII (personally identifiable information: names, emails, phone numbers, addresses, card numbers) should be replaced with placeholders before a log is stored. That is redaction. Do it at write time; removing it later is much harder.

Set a retention period

Retention is how long you keep a record before deleting it. Long enough to debug last month's complaint, short enough that a leak is bounded. Thirty to ninety days is a common rule of thumb.

Key idea

If you cannot replay a bad answer with the exact prompt, model and inputs that produced it, you cannot fix it. Log every call as a trace from day one. It is far cheaper than adding logging after the first complaint you cannot reproduce.

Common doubt

"Isn't storing every prompt expensive, and a bit creepy?" Text is cheap compared with the model calls that produced it. The creepy part is real, which is why you redact, keep logs for a limited time, tell users what you keep (Step 9), and restrict who can read them.

Step 6 · Still good?

Quality in production

Your offline eval set said the feature was good before launch. Real users will disagree in ways you did not test for. This is how you keep measuring after launch.

Part 5 introduced online evals: measuring quality on live traffic instead of a fixed test set. Offline evals tell you whether a change is safe to ship. Online evals tell you whether the shipped thing is actually good for the people using it. You need both, and the interesting part is the loop between them.

Offline decides what ships. Online decides what to fix next. Failures found online go into the offline set so they can never come back unnoticed.

Signals you can collect from live traffic

Explicit feedback

Thumbs up and down, a star rating, a "was this helpful?" button. Cheap to add. Few users click, and those who do are usually annoyed, so treat the rate as a trend, not a score.

Implicit signals

What users do: retry the same question, copy the answer, click the suggested link, escalate to a human? A retry within a minute is a strong "that was not it".

LLM judge on a sample

Run the judge from Part 5 on a random slice of live conversations every day, with the same rubric you use offline. Now you have a quality number that moves when the product changes.

A/B tests

An A/B test shows version A to some users and version B to the rest, then compares their signals. It is the only honest way to know whether prompt v13 beats v12 for real people. Assign whole users, not single requests, pick the metric in advance, and run until a few hundred users have seen each side.

Drift: when the questions change under you

Drift is the slow change in what users ask over time. You launched a recipe assistant; six months later a third of questions are about the new meal-planning feature, which your eval set has never heard of. Your offline score is still fine and your real quality has dropped. Watch for it by sampling recent questions and asking "is this kind of question in my eval set?" If not, add it.

Analogy

Comment cards on the tables are explicit feedback. Plates coming back half eaten are implicit signals. A secret diner with a checklist is the LLM judge on a sample. Serving the new sauce at half the tables for a week is the A/B test. Drift is the neighbourhood changing: this year's customers want different dishes from the ones you opened with.

Key idea

Offline evals catch what you already know to test. Online signals catch what you did not know. The habit that ties them together: every failure found in production becomes an item in the offline set, so the same mistake is caught by the gate next time.

Common doubt

"Only 2% of users click thumbs-down. Is that even useful?" Very. You are not using it as a score; you are using it as a stream of failures to read. Fifty thumbs-downs a day is fifty real bad answers, each with a full trace. That is a better eval set than anything you could write yourself.

Step 7 · Which model

Choosing and routing models

Big or small, hosted or self-run, one model or several. How to decide, and how to keep the decision reversible.

Big versus small

Large models handle hard, open-ended tasks better. Small models are faster and cheaper per token, and for easy tasks just as good. Most products have a mix, which suggests the trick: do not pick one model, pick a rule.

A router is code that looks at each request and decides which model handles it. The rule can be simple (a short question goes to the small model; anything mentioning a refund goes to the large one) or a tiny classifier. A common pattern is "try small first; if the output fails validation or the model says it is unsure, escalate to the large one".

Analogy

A hospital does not send every patient to the senior consultant. A triage nurse sends a sprained ankle to the walk-in clinic and chest pain to the specialist. The nurse is the router. The clinic is the small model: fast, cheap, right for most cases. The specialist is the large model: slower, costlier, and the only correct choice for the hard cases.

Hosted API versus self-hosting

With a hosted API, a provider runs the model and you pay per token. With self-hosting, you run an open-weight model (one whose trained parameters are published so anyone can run it, see Part 6) on computers you control. That needs an inference server, software whose job is to run a model efficiently for many users at once (vLLM is a widely used open-source example), and GPUs, the graphics processors that do the heavy arithmetic. To make it cheaper, people use quantization: rounding the model's numbers to fewer bits so it needs less memory and runs faster, at a small cost in quality that your eval set should confirm before you trust it.

Keep the decision reversible

Whatever you choose, you will want to switch later: a better model appears, prices change, a provider has a bad month. Two habits make switching cheap:

  • Abstract the client. All your code calls one function of your own (like call_model), and only that function knows which provider is behind it. Switching becomes a one-file change.
  • Keep your evals. The eval set from Part 5 is how you compare candidates fairly. Run it against the new model, read the failures, then switch gradually (Step 8).
Key idea

There is no best model, only the best model for this request at this price. Route easy work to small models, keep the large one for hard cases, hide the provider behind your own function, and let your eval set, not the marketing page, decide when to switch.

Common doubt

"Is self-hosting cheaper?" Only sometimes. A GPU costs the same busy or idle, so self-hosting wins with high, steady volume and people who already run servers. For a small or bursty workload, paying per token is almost always cheaper once you count engineers' time. Start hosted; move if the numbers or the data rules force you.

Step 8 · Changing things

Shipping changes safely

Every prompt edit and every model swap is a release. Here is the pipeline that stops a "tiny tweak" from breaking the feature for everyone.

The most useful mental shift in this guide: prompts and model choices are configuration, and configuration is code. It lives in version control. It goes through tests. It is released gradually. It can be rolled back. Editing a prompt in a text box on a Friday afternoon is how most incidents with LLM features begin.

One prompt change travelling through the release pipeline. It is tested before anyone sees it, shown to a few users first, watched, and only then given to everyone.

The pieces of the pipeline

Version everything

Prompt text, model name, temperature, max tokens, retrieval settings. Each combination gets a version number, and every trace records which version produced it.

Eval gate in CI

CI (continuous integration) is the automation that runs tests on every change. An eval gate runs the offline eval set there and blocks the release if the score drops. Part 5 built the set; this is where it earns its keep.

Canary release

A canary release sends the new version to a small share of users (1% to 10%) while everyone else keeps the old one. If its metrics look worse, few people were affected.

Feature flags

A feature flag is a switch in your config that decides which version a user gets, changeable without redeploying. It is how you do canaries, A/B tests and instant rollbacks.

Rollback plan

A rollback returns to the previous version. Write down before release exactly how (usually "flip the flag back") and practise it once. A rollback you have never done is not a plan.

Changelog

One line per prompt version: what changed, why, and the eval score. When someone asks in six months why the bot stopped apologising so much, this is the only record.

Analogy

A restaurant chain does not change the sauce on all four hundred menus overnight. The test kitchen tries it (the eval gate). One branch serves it for a fortnight (the canary). Head office watches sales and complaints (the dashboard). The old recipe stays in the binder (the rollback), with a dated note saying what changed and why (the changelog).

Key idea

Treat a prompt edit with the same respect as a code change: version it, test it, release it to a few, watch, then release it to all, and keep the old one ready. The ceremony costs minutes. The incident it prevents costs days.

Common doubt

"It's a one-word prompt tweak. Do I really need all this?" One-word changes are exactly the ones that surprise people. "Be concise" can make a model drop the safety disclaimer; "always cite sources" can make it invent them. The eval gate takes minutes and runs itself. Let it.

Step 9 · Trust

Privacy, compliance, and data handling

Your users' words are travelling to a third party's computers. What to find out, what to decide, and when to call your legal team. Practical guidance, not legal advice.

Every request to a hosted model sends your users' text to the provider. That is fine when everyone knows and has agreed, and a serious problem when they have not. The questions below are the ones a careful team answers before launch. None is hard; they only require looking.

What leaves your systems?

List it: the user's message, the history, retrieved documents, tool results. If any of it can contain personal or confidential data, the rest of this list applies to you.

How long does the provider keep it?

Read the provider's retention policy. Some keep request data briefly for abuse monitoring; some offer zero-retention options.

Is it used for training?

Check whether your data may train the provider's future models, and whether you can opt out. Business agreements usually exclude training; consumer terms sometimes do not.

Where is it processed?

Some laws require personal data to stay in a region. Many providers offer regional hosting. If your users are somewhere regulated, ask for it.

Are your own logs protected?

Encrypt stored traces, restrict who can read them, redact PII before storage (Step 5), and delete them at the end of the retention period.

Do users know and agree?

Say plainly, in your privacy notice and in the product, that an AI provider processes their messages. Consent should be informed, not buried.

Can you delete on request?

When a user asks you to delete their data, you must find every trace containing it, in your logs and, where possible, at the provider. Design for this early.

What does the SLA say?

A service level agreement (SLA) is the provider's written promise about uptime and support, and what you get if they miss it. Read it before promising anything to your own customers.

Analogy

Using a hosted model is like sending documents to an outside accountant. Sensible questions first: what do they keep copies of, for how long, do they reuse your figures to train their juniors, which country is their office in, and have your clients agreed? Good answers make it a normal business arrangement. No answers make it a risk.

Watch out

Terms of service change. The answer you got at launch may not hold next year. Put a reminder in the calendar to re-read the provider's data terms twice a year, and whenever you switch providers.

Key idea

Privacy work is mostly knowing: what data you send, what the provider does with it, and what you told your users. Write the answers on one page. Then check with your legal team, because the rules depend on where you and your users are, and this guide cannot know that.

Common doubt

"We're a tiny startup. Does any of this apply to us?" Yes, from the first user. The good news is the work is small at the start: one page of answers, a redaction step in your logging, a sentence in your privacy notice. It gets hard only if you skip it and retrofit it after a customer asks.

ReliabilityThere is a tested fallback and a graceful message if it also fails.Users get something useful instead of an error screen.
ReliabilityStructured outputs are validated, and max tokens is set.Broken JSON and runaway answers are caught before the user or the bill sees them.
ReliabilityYou know your rate limits and expected peak traffic.Launch day is when you find out otherwise.
SpeedAnswers are streamed wherever a person is reading them.Time to first token is what users feel.
SpeedYou have measured p50 and p95 latency and set a target.Averages hide the slow requests users remember.
SpeedPrompts and answers are as short as the task allows.Output length is the biggest lever for both speed and cost.
CostYou know the cost per request and the projected monthly bill.Surprises on the invoice get features switched off.
CostPrompt caching is used, with stable content first in the prompt.Re-sending the same long prefix on every call is pure waste.
CostThere is a daily cost alert.A retry loop or a runaway agent should page you within hours, not at month end.
ObservabilityEvery call is logged as a trace with prompt version, tokens, latency and cost.Without this you cannot reproduce a complaint.
ObservabilityPII is redacted before storage and logs have a retention period.Bounded logs bound the damage of a leak.
ObservabilitySomeone reads a sample of traces and every thumbs-down each week.Metrics find what you measure; reading finds the rest.
ObservabilityAlerts exist for p95 latency, error rate and fallback rate.You should learn about an outage from a page, not a tweet.
ChangePrompts and model settings are versioned, each with a changelog line.You cannot roll back to a version you did not record.
ChangeThe offline eval runs in CI and blocks a release if the score drops.The cheapest place to catch a regression is before anyone sees it.
ChangeNew versions go out as a canary behind a feature flag, with a practised rollback.A bad change should affect 5% of users for an hour, not everyone for a day.
Key idea

You will not tick every box before your first launch, and that is fine. The point is to choose which ones to leave, write the choice down, and come back to it. The boxes you skip by accident are the ones that page you.

Practical tip

If you can only do three things this week: add a timeout and capped retry to every call, log every call as a trace with the prompt version, and set a daily cost alert. Those three catch most first-month incidents.

Step 11 · Check yourself

Quiz and glossary

Six quick questions. Click an answer to see whether you got it. Then a glossary of every term in this guide, for looking things up later.

Glossary

A/B test
Showing version A to some users and version B to others, then comparing their behaviour to see which is better.
Alert
A rule that notifies a person when a measurement crosses a line, such as p95 latency above a limit.
API
Application programming interface: the agreed way for one program to ask another program to do something.
Cache
A store of results from earlier work, kept so the work does not have to be repeated.
Cache hit
When the thing you need is already in the cache. A miss is when it is not.
Canary release
Releasing a new version to a small share of users first, and watching before giving it to everyone.
CI (continuous integration)
Automation that runs tests on every change to code or configuration before it can be released.
Circuit breaker
A guard that stops calling a failing service for a cooling-off period after repeated failures, then tests whether it has recovered.
Cost per request
What one typical call costs: input tokens times input price plus output tokens times output price.
Dashboard
A page of charts built from logs: latency, errors, cost, feedback.
Drift
The slow change in what users ask over time, which makes an old eval set less representative.
Endpoint
The specific address you send an API request to.
Eval gate
An automated check that runs the offline eval set and blocks a release if the score drops.
Exponential backoff
Waiting longer before each retry, typically doubling: 1 s, 2 s, 4 s.
Fallback
A second option (another model, provider or prompt) used when the first one fails.
Feature flag
A switch in configuration that decides which version a user gets, changeable without redeploying.
GPU
Graphics processing unit: the chip that does the heavy arithmetic of running a model.
Graceful degradation
Giving a simpler but useful result (a cached answer, a helpful message) instead of an error.
Idempotency
The property that doing an operation twice has the same effect as doing it once, which makes it safe to retry.
Inference server
Software that runs a model efficiently for many users at once. vLLM is a widely used open-source example.
Jitter
A small random amount added to a retry wait so many clients do not retry at the same instant.
Latency
How long you wait for a result. For model calls, see time to first token and total time.
Logging
Writing records of what happened somewhere you can search later.
Max tokens
The longest output you will accept from one call; a ceiling on time and cost.
Messages list
The conversation so far, sent with each request: system instructions, user turns and assistant turns.
Observability
Being able to understand what a system did from the records it left behind.
Online eval
Measuring quality on live traffic (feedback, judged samples, A/B tests) instead of a fixed test set.
Open-weight
A model whose trained parameters are published, so anyone can download and run it.
Percentile (p50 / p95)
p50 is the middle value of all measurements; p95 is the value that 95% of measurements are better than. p95 exposes the slow tail.
PII
Personally identifiable information: names, emails, phone numbers, addresses, anything that points to a person.
Prompt caching
The provider reusing its processed reading of an unchanged prompt prefix, making it cheaper and faster.
Quantization
Storing a model's numbers with less precision so it needs less memory and runs faster, at a small cost in quality.
Rate limit
The maximum requests or tokens per minute a provider lets you send before refusing with a "slow down" error.
Redaction
Replacing personal data with placeholders before a record is stored.
Request
What your app sends to the API: the messages list plus settings.
Response
What comes back: the model's text plus token counts and status.
Response caching
Storing the exact answer to an exact input so a repeated request needs no model call.
Retention
How long data is kept before it is deleted, both in your logs and at the provider.
Retry
Trying a failed operation again, ideally only for temporary failures and with a cap.
Rollback
Returning to the previous version after a release goes wrong.
Router
Code that decides which model handles each request, for example small for easy and large for hard.
Self-hosting
Running an open-weight model on computers you control instead of calling a provider.
Semantic cache
A cache that reuses an answer for a question that means the same as one seen before, judged by embedding similarity.
SLA (service level agreement)
A provider's written promise about uptime and support, and what happens if they miss it.
Span
One named step inside a trace, with a start time, an end time and details. Spans nest.
Streaming
Receiving tokens one by one as they are generated, instead of waiting for the whole answer.
Throughput
How much work is done per second overall: tokens per second, or requests per second.
Time to first token
The wait from sending a request until the first token arrives. It grows with input size and is what users feel.
Timeout
The longest you will wait for a response before giving up.
Token
The unit models read and write in: roughly a word or part of a word. You are charged per token.
Trace
The complete record of one request from start to finish, made of nested spans.
