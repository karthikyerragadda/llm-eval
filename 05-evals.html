Step 0 · 2 minutes

Before we start: what an LLM actually is

You only need one idea from this chapter, and it explains why evals exist at all.

A Large Language Model (LLM) is a program that reads some text and predicts what text should come next. It does this one small piece at a time (a piece is called a token, roughly a word or part of a word). It repeats "predict the next token" until it has written a full answer.

Analogy

Imagine a student who has read almost the entire internet, but only ever practised one game: "finish this sentence". They got astonishingly good at it. Ask them anything and they will produce a fluent, confident answer. But fluent and confident is not the same as correct.

Key idea

An LLM does not know whether its answer is right. It produces the most plausible text. Three consequences follow:

  • It can be confidently wrong (people call this hallucination).
  • It can give a different answer to the same question on a different day.
  • A tiny change in wording can change its behaviour a lot.

So we cannot just trust it. We have to measure it. That measuring is evaluation.

Step 1 · The basics

What is an "eval"?

Definition, the exam analogy you will use for the rest of this guide, and why people bother.

Evaluation (short: eval) is a systematic, repeatable way to measure how well an LLM, or a product built on top of an LLM, does a particular job.

The word "eval" is used for both the activity ("we ran an eval") and the thing ("we built an eval for our support bot"). Both meanings are fine.

Analogy: the school exam

Think of how a school checks whether a student learned the subject. Nobody just asks "do you feel like you know maths?" They give an exam. The exam has fixed questions, an answer key, and a teacher who grades. Then the student gets a mark. An LLM eval has exactly the same five pieces.

Why do people bother with evals?

1. You cannot improve what you cannot measure

If you change a prompt or switch models, did it get better or worse? Without a number, you are guessing.

2. LLMs fail silently

Bad answers look just as polished as good ones. Only a check against the truth catches them.

3. Choosing between options

Model A or model B? Prompt v3 or v4? Evals turn arguments into comparisons.

4. Catching regressions

A fix for one problem often breaks something else. Re-running the eval catches it before your users do.

"Vibe check" versus a real eval

Most people start by typing a few questions into the model and looking at the answers. That is called a vibe check. It is useful for a first impression, but it does not scale.

Vibe check

  • 5 questions you happened to think of
  • You judge by feel, on the spot
  • Different every time you do it
  • Cannot tell 88% from 91%

Eval

  • Hundreds of questions, chosen on purpose
  • A written rule for what "correct" means
  • Same test every time, so results are comparable
  • Produces a number and a list of failures
Common doubt

"Isn't the model's training already a kind of test?" No. Training teaches the model to predict text. It never checks whether the model can do your task. That is why every team builds evals for their own use case.

Step 2 · The pipeline

Anatomy of an eval

Every eval, from a 10-line script to a famous benchmark, is the same six-stage pipeline. Watch one item flow through it.

The red dot is one test item travelling through the pipeline. One item gives you one grade. Many items give you a metric.

The six pieces, one by one

1Dataset

A list of test items. Each item has an input and usually an expected output (also called the reference, gold label, or ground truth).

{"input": "What is 17 × 3?", "expected": "51"}

2Prompt

How the input is wrapped before sending it to the model: instructions, examples, formatting rules. The prompt is part of what you are testing.

3Model

The LLM being tested, with its settings (for example temperature, which controls randomness).

4Output

Whatever the model wrote back. Usually text, sometimes structured data, code, or a sequence of tool calls.

5Grader

The rule that turns one output into a score. Can be code, another model, or a human. This is the most important design choice, so it gets its own chapter.

6Metric

The summary number across all items: accuracy, average score, pass rate, win rate. This is what you put on a chart.

Key idea

An eval score is only as meaningful as its dataset and its grader. A perfect metric on a silly dataset, or a strict dataset with a sloppy grader, tells you nothing. When someone says "the model scores 94%", your first two questions should be: 94% on what questions, and graded how?

Go deeper: words you will hear around this pipeline
  • Sample / item / example: one row in the dataset.
  • Reference / gold / ground truth / label: the expected answer.
  • Eval set / test set: the dataset used for evaluation. It must be kept separate from anything the model was trained on.
  • Harness: the code that runs the whole pipeline for you.
  • Zero-shot / few-shot: whether the prompt includes zero or a few worked examples before the real question.
  • Run: one full pass over the dataset with one specific model and prompt. Comparing runs is how you make decisions.
Step 3 · What we test

Types of tasks

Different jobs need different exams. The one question that matters: does the task have one right answer, or many acceptable ones?

Classification

Pick a label from a fixed list.

"Is this email spam?" → yes / no

Extraction

Pull specific facts out of text.

"Find the invoice date" → 2026-03-14

Closed question answering

Factual questions with a short, checkable answer.

"Capital of Peru?" → Lima

Maths and reasoning

Multi-step problems with a final answer.

word problems, logic puzzles

Code generation

Write a program that does X.

"Write a function that reverses a list"

Summarisation

Compress a long text without losing the point.

"Summarise this article in 3 sentences"

Open generation

Write something new with no single right answer.

emails, stories, marketing copy

Conversation

Multi-turn chat where context builds up.

customer support, tutoring

Agents

Take actions using tools over many steps to finish a task.

"Book me a flight and add it to my calendar"

The spectrum that decides everything

One right answerMany good answers
ClassificationExtractionClosed QAMathsCodeSummariesEmailsStories

On the left, grading is easy: compare the output with the answer key. On the right, there is no single answer key. "Write a polite refusal email" has thousands of good answers. Grading there needs judgment, which is harder and more expensive. The next chapter is about exactly this.

Analogy

A multiple-choice maths test can be graded by a machine in seconds. An essay needs a teacher reading it with a rubric. Same school, very different grading effort. LLM tasks are the same.

Common doubt

"Can I turn an open task into a closed one?" Often, yes, and it is a great trick. Instead of grading the whole email, check specific things: does it contain the customer's name, does it stay under 120 words, does it avoid the word "unfortunately"? Each of those is a yes/no check. You lose some nuance but gain reliability.

Step 4 · The heart of it

How do we grade an answer?

Seven grading methods, from the strictest and cheapest to the most flexible and most expensive. Then a playground to feel the difference.

A grader (also called a scorer) takes one model output and returns a score. Here is the ladder. Lower rungs are cheap and rigid. Higher rungs are flexible and costly.

1

Exact match

Is the output exactly the expected string? Great for labels, numbers, and multiple choice. Fails on "Paris." versus "Paris".

Flexibility Cost
2

Normalised or rule-based match

Clean both strings first (lowercase, remove punctuation and words like "the"), then compare. Or check with rules: contains the keyword, matches a pattern, number within ±0.01, valid JSON, under 100 words.

Flexibility Cost
3

Overlap metrics (F1, BLEU, ROUGE)

Count how many words the output shares with the reference. Token F1 is the simple one. BLEU (translation) and ROUGE (summaries) are older cousins. They measure word overlap, not meaning, so a correct paraphrase can score badly.

Flexibility Cost
4

Semantic similarity (embeddings)

Convert both texts into vectors of numbers that capture meaning, then measure how close they are. "The capital is Paris" and "Paris is the capital" land close together. Good for "roughly the same meaning", bad at catching a single wrong fact.

Flexibility Cost
5

Execution-based (run it)

For code: run the generated program against unit tests. For SQL: run the query and compare rows. For agents: check the final state (was the ticket really created?). Ignores how the answer looks and checks whether it works.

Flexibility Cost
6

LLM-as-a-judge

Ask a strong LLM to grade the answer using a written rubric. Three common forms: score one answer from 1 to 5; compare two answers and pick the better one (pairwise); or grade against a reference answer. Flexible and scalable, but the judge has its own biases (see Pitfalls).

Flexibility Cost
7

Human evaluation

People read and rate the outputs. The gold standard for quality, taste, and safety. Slow, expensive, and humans disagree with each other, so you need clear guidelines and several raters per item.

Flexibility Cost
Analogy

Rung 1 is a scantron machine. Rung 3 is a teacher counting keywords in an essay. Rung 5 is a driving test: nobody cares how you describe parking, they watch whether the car ends up in the space. Rung 6 is a teaching assistant grading with a rubric. Rung 7 is the professor reading every essay personally.

Go deeper: how to write a good LLM-judge prompt

A judge is only as good as its rubric. A solid judge prompt has:

  1. The task context: what the original user asked and what a great answer must do.
  2. Explicit criteria: "Correct facts", "Answers the actual question", "Under 100 words", "No made-up policies". Each criterion should be checkable.
  3. A scale with anchors: what a 1 looks like, what a 5 looks like. Or better: yes/no per criterion, then add them up.
  4. A reference answer when one exists. Judges are far more reliable when they compare against something.
  5. Reasoning before the score: ask the judge to explain first, then output the score in a fixed format you can parse.

Then validate the judge: take 50 to 100 items, grade them by hand, and check how often the judge agrees with you. If agreement is low, fix the rubric before trusting the judge on thousands of items.

Step 5 · Numbers

Metrics: turning grades into one number

The handful of metrics you will see everywhere, explained with a fishing net, plus why small eval sets lie.

Accuracy

The simplest metric: items graded correct, divided by all items. "188 out of 200 correct" is 94% accuracy. Use it whenever every item is a simple pass or fail and mistakes are equally bad in both directions.

Precision, recall, and F1

These matter when the model is trying to find things (spam, toxic messages, names in a document) and the two kinds of mistake are different.

Analogy: the fishing net

You cast a net into a lake to catch fish.

  • Precision: of everything in your net, what fraction is actually fish (and not boots and seaweed)? High precision means few false alarms.
  • Recall: of all the fish in the lake, what fraction did you catch? High recall means few misses.
  • F1: one number that balances both. It is high only if precision and recall are both high.

A giant net catches every fish (high recall) but also all the junk (low precision). A tiny net catches only fish (high precision) but misses most of them (low recall).

Other metrics you will meet

pass@k

Used for code. Give the model k attempts; the item passes if at least one attempt passes the tests. pass@1 is the strictest.

Win rate

From pairwise judging. Out of all head-to-head comparisons, how often did model A beat model B? 50% means a tie.

Elo / Bradley-Terry rating

Turns many pairwise wins into a single ranking number, like chess ratings. Used by public arenas where humans vote.

Mean rubric score

Average of judge scores (say 1 to 5) across items. Always look at the distribution too, not only the mean.

Perplexity

How "surprised" the model is by real text. Lower is better. Used when training base models, rarely useful for judging a product.

Latency, cost, tokens

Not quality metrics, but every real decision weighs quality against speed and price. Track them in the same run.

How many test items do you need?

Scores from small eval sets bounce around by luck. The table shows roughly how much a measured accuracy could be off from the truth, just from random chance, at different sizes.

Items in eval setTypical margin of errorWhat it means
25about ±20 pointsCannot tell 70% from 90%. Fine for spotting obvious breakage only.
100about ±10 pointsGood enough to see big improvements.
400about ±5 pointsCan compare two decent prompts.
1,600about ±2.5 pointsNeeded to trust a "2% better" claim.

Rule of thumb: to halve the error, you need four times as many items. These are 95% confidence ranges at 50% accuracy, the worst case.

Key idea

A single number hides everything interesting. Always look at which items failed and why. The metric tells you whether to worry; the failures tell you what to fix.

Step 6 · Public exams

Benchmarks: the exams everyone takes

What a benchmark is, the famous ones you will see in every model announcement, and why a top score can still mean little for you.

A benchmark is a fixed, public eval: a shared dataset plus a shared grading rule, so different models can be compared fairly. A leaderboard is the ranked list of results.

Analogy

Benchmarks are standardised exams like the SAT or JEE. Everyone sits the same paper, so scores are comparable across schools. But a high SAT score does not tell an employer whether you can do their specific job. That is what your own eval is for.

Three warnings about benchmark scores

1Saturation

When every top model scores 90%+, the benchmark can no longer separate them. Old benchmarks retire; new, harder ones appear.

2Contamination

Benchmark questions leak onto the internet, get scraped into training data, and the model has effectively seen the exam paper in advance.

3Not your task

A model that tops the maths leaderboard can still write terrible support emails in your brand's voice. Benchmarks help you shortlist; your own eval decides.

Go deeper: reading a model announcement critically

When a company publishes a table of benchmark numbers, check the fine print:

  • Same settings? Zero-shot vs 5-shot, with or without chain-of-thought, pass@1 vs pass@5 change scores a lot. Comparisons are only fair with identical settings.
  • Who ran it? Self-reported numbers versus independent re-runs often differ by a few points.
  • Which version? "SWE-bench" and "SWE-bench Verified" are different datasets with different difficulty.
  • Error bars? A 0.8 point gain on a 500-item benchmark is inside the noise.
Step 7 · Where evals lie

Pitfalls: how an eval can fool you

The ways a clean-looking number can be wrong, and the habits that protect you.

Goodhart's law

"When a measure becomes a target, it stops being a good measure." Optimise hard for one metric and the model learns to game it: longer answers to please a judge, keyword stuffing to please ROUGE.

Randomness

At temperature above 0 the model gives different answers each run. Run the eval several times, or set temperature to 0, and report the spread, not one lucky number.

Prompt sensitivity

Changing "Answer:" to "Answer :" can shift a score by several points. Test a few phrasings before concluding one model is better.

Too few items

Twenty examples cannot distinguish 80% from 90%. See the margin-of-error table in Step 5.

Overfitting your own eval

If you tweak the prompt until the eval set passes, you have taught the prompt that specific set. Keep a held-out portion you never look at while tuning.

Metric mismatch

ROUGE rewards a summary that copies sentences and punishes a better paraphrase. Pick a grader that measures what you actually care about.

Stale eval sets

Users change, products change. An eval built last year may not represent this year's questions. Refresh it with real, recent examples.

Judge biases

LLM judges prefer longer answers (verbosity bias), the first answer shown (position bias), and answers in their own style (self-preference). Try it below.

Playground

Position bias, live

A naive judge is asked "which answer is better, A or B?". Below is a simulated judge with a mild habit of favouring whatever comes first. Swap the order and watch the verdict.

Answer A

Judge says: Answer A is better.
The short, precise answer is in position A.

The fix: judge every pair twice, once in each order, and count it as a tie if the judge disagrees with itself. Also tell the judge explicitly that length is not quality.

The biggest trap of all

Contamination. If the test questions were in the training data, the score measures memory, not ability. Public benchmarks suffer from this constantly. For your own evals, keep the set private and never paste it into a prompt you use for training or fine-tuning.

Step 8 · The real world

Evaluating your own application

Benchmarks test models. You ship products. A product is a model plus a prompt plus data plus tools, and each part needs testing.

Model evals versus application evals

Model eval

  • Question: "How capable is this model in general?"
  • Public benchmarks, broad tasks
  • Done by labs and researchers
  • Helps you shortlist a model

Application eval

  • Question: "Does my product work for my users?"
  • Your own dataset, your prompt, your data, your tools
  • Done by the team that ships it
  • Decides what goes to production

The kinds of application evals

Capability evals

Can it do the core job? "Answers the customer's question correctly."

Regression evals

Did today's change break anything that worked yesterday? Run on every prompt or model change, like unit tests for software.

Safety evals

Does it refuse harmful requests, avoid leaking private data, resist prompt injection, stay on topic?

Format evals

Valid JSON every time? Under the length limit? Uses the required sections?

Special case: RAG (retrieval-augmented generation)

Many apps first search your documents, then hand the results to the model to write an answer. That is RAG. It has three places to fail, so it is evaluated as a triangle.

Each edge of the triangle is one check, usually done with an LLM judge. A low score on one edge tells you exactly which part of the system to fix.

Special case: agents

An agent takes many steps, calling tools (search, calculator, APIs) along the way. You evaluate both the destination and the journey:

  • Task success: was the goal reached? Check the final state, not the model's claim that it finished.
  • Trajectory quality: did it call the right tools with the right arguments, in a sensible order, without loops?
  • Efficiency: how many steps, tokens, and seconds did it take?
  • Safety: did it avoid destructive actions it was not asked for?

Building your own eval set

  1. Start from real inputs. Pull actual user questions from logs, or write 20 to 50 realistic ones with a colleague. Real questions are messier than the ones you invent.
  2. Collect failures. Every time the app embarrasses you, add that input to the set. Failures are the most valuable items you own.
  3. Write the expected output or a rubric. For closed tasks, the exact answer. For open tasks, a checklist of what a good answer must and must not contain.
  4. Pick a grader per item. Mix cheap code checks with a judge for the subjective parts.
  5. Version it. Keep the set in the repo, next to the code. When it changes, scores from before are not comparable.
  6. Grow it. 30 items is a fine start. Aim for a few hundred over time, covering the cases that matter most.

Offline versus online

Offline eval (before shipping)

  • Fixed dataset, run on demand
  • Reproducible, cheap to repeat
  • Gate: "do not deploy if the score drops"

Online eval (in production)

  • Real traffic, real users
  • Thumbs up/down, judge a sample of live answers, A/B tests
  • Feeds new failures back into the offline set
Practical tip

The most common mistake teams make is spending weeks on the perfect metric and zero hours reading outputs. Start with 30 examples and a simple grader. Read every failure. You will learn more in an afternoon than from a month of dashboards.

Step 9 · The habit

The eval loop: how good teams actually work

Evals are not a one-time exam. They are a loop you run every time you change anything.

A worked example: a customer-support bot

  1. Build. You write a prompt: "You are a helpful support agent for Acme. Answer using the policy document below."
  2. Run evals. 60 real customer questions go through. Grader: an LLM judge with a rubric (correct per policy, polite, under 120 words). Score: 3.9 / 5.
  3. Read failures. You read the 14 lowest-scoring answers. 9 of them invent a refund window that is not in the policy. That is a pattern.
  4. Fix. You add one line: "If the policy does not state a number, say you will check and do not guess."
  5. Compare. Re-run the same 60. Score: 4.4 / 5. Invented numbers: 1. Nothing else got worse. Ship it, and add those 9 questions to the permanent regression set.
Key idea

The metric got you to look. The failures told you what to change. Step 3, reading the actual outputs, is the step that most people skip and the step that matters most. Experienced practitioners call this error analysis.

Go deeper: the three-level habit
  • Level 1: unit-style checks. Fast, cheap, run on every change. Format checks, exact matches, "does not contain competitor names". Hundreds per second.
  • Level 2: model-graded evals. LLM judge on a few hundred items. Run before each release or nightly.
  • Level 3: human review and A/B tests. Slow and expensive. Run for big decisions: a new model, a redesign, a launch. Also used to check that the level-2 judge still agrees with people.
Step 10 · Hands-on

A complete eval in about 40 lines of Python

No framework, no magic. Every piece from Step 2 is visible. Replace call_model with any LLM API you like.

# eval.py — the six pieces of an eval, in plain Python

def call_model(prompt: str) -> str:
    # Put any LLM API call here. Return the model's text.
    ...

# 1. DATASET: the exam paper with its answer key
dataset = [
    {"input": "What is the capital of France?", "expected": "Paris"},
    {"input": "What is 17 * 3?",                "expected": "51"},
    {"input": "Who wrote Hamlet?",              "expected": "Shakespeare"},
]

# 2. PROMPT: how each input is wrapped
def build_prompt(question: str) -> str:
    return f"Answer in as few words as possible.\nQuestion: {question}\nAnswer:"

# 5. GRADERS: two ways to score one output
def grade_contains(output: str, expected: str) -> bool:
    # rung 2 on the ladder: normalised, rule-based
    return expected.lower() in output.lower()

def grade_with_judge(question: str, output: str, expected: str) -> bool:
    # rung 6: LLM-as-a-judge with a reference answer
    verdict = call_model(
        f"Question: {question}\nReference answer: {expected}\n"
        f"Candidate answer: {output}\n"
        f"Does the candidate mean the same as the reference? Reply YES or NO."
    )
    return verdict.strip().upper().startswith("YES")

# 3 + 4. MODEL and OUTPUT: run every item
results = []
for item in dataset:
    output = call_model(build_prompt(item["input"]))
    results.append({
        **item,
        "output": output,
        "pass": grade_contains(output, item["expected"]),
    })

# 6. METRIC: accuracy, plus the failures to read
accuracy = sum(r["pass"] for r in results) / len(results)
print(f"accuracy = {accuracy:.0%}  ({len(results)} items)")
for r in results:
    if not r["pass"]:
        print("FAIL:", r["input"], "→", r["output"])

That is a real eval. Everything else in the field is this script with more items, better graders, nicer reports, and automation.

Tools people use instead of writing it by hand

lm-evaluation-harness

The standard open-source runner for academic benchmarks (MMLU, GSM8K and hundreds more).

Inspect AI

Open-source framework from the UK AI Safety Institute. Clean Python API for datasets, solvers, and scorers, including agents.

promptfoo

Config-file driven. Compare prompts and models side by side, with built-in assertions and judges.

RAGAS, DeepEval

Libraries with ready-made metrics for RAG (faithfulness, relevance) and general LLM apps.

Braintrust, Langfuse, LangSmith

Hosted platforms that store datasets, run evals, log production traces, and show dashboards.

A spreadsheet

Honestly fine for your first 50 items. Input, output, expected, pass/fail, notes. Upgrade when it hurts.

Common doubt

"Which tool should I start with?" Start with the script above, or a spreadsheet. Tools save time once you know what you want to measure. They do not tell you what to measure.

Step 11 · Check yourself

Quiz and glossary

Six quick questions. Click an answer to see whether you got it. Then a glossary for looking things up later.

Glossary

Agent
An LLM that takes multiple steps and uses tools to complete a task.
Benchmark
A public, fixed eval that lets different models be compared.
BLEU / ROUGE
Older overlap metrics that count shared words between an output and a reference. BLEU is used for translation, ROUGE for summaries.
Chain-of-thought
Asking the model to reason step by step before answering. Changes scores a lot, so eval settings must say whether it was used.
Confusion matrix
The 2 by 2 table of true positives, false positives, false negatives, and true negatives that precision and recall are computed from.
Contamination
Test questions ending up in the training data, inflating scores.
Dataset / eval set
The list of test inputs, usually with expected outputs.
Elo / Bradley-Terry
Rating systems that turn many pairwise wins and losses into one ranking number, as in chess.
Embedding
A list of numbers that captures the meaning of a text, so similar meanings land close together. Used for semantic-similarity grading.
Error analysis
Reading the failed items to find patterns worth fixing.
Eval
A repeatable test that measures how well a model or app does a job.
Few-shot / zero-shot
Whether the prompt includes a few worked examples (few-shot) or none (zero-shot). Both are eval settings that must be reported.
Goodhart's law
"When a measure becomes a target, it stops being a good measure." Optimising hard for one metric makes the model game it.
Grader / scorer
The rule or model that scores one output.
Ground truth / reference
The expected, correct answer for an item.
Hallucination
A fluent but false statement produced by the model.
Harness
The code that runs the whole eval pipeline: loads the dataset, calls the model, grades, and reports.
Held-out set
Items you keep hidden while tuning, to check you did not overfit.
Leaderboard
A ranked table of benchmark results.
LLM-as-a-judge
Using a strong model to grade another model's output.
Metric
A summary number over the whole dataset (accuracy, F1, win rate).
Offline / online eval
Testing on a fixed set before shipping, versus measuring on live traffic after.
Pairwise
Comparing two outputs and picking the better one, instead of scoring each alone.
pass@k
Fraction of items solved in at least one of k attempts.
Position bias
An LLM judge's habit of preferring whichever answer is shown first.
Precision / recall / F1
False-alarm rate, miss rate, and their balance. See the fishing net.
RAG
Retrieval-augmented generation: search documents first, then answer using them.
Regression
Something that used to work and now fails after a change.
Rubric
A written checklist of what a good answer must have. Used by human and LLM judges.
Saturation
When most models score near the top and the benchmark stops discriminating.
Temperature
A setting for randomness. 0 is most deterministic.
Token
The unit a model reads and writes, roughly three quarters of an English word. Eval cost and latency are counted in tokens.
Verbosity bias
An LLM judge's habit of preferring longer answers even when they are not better.
Vibe check
Trying a few questions by hand and judging by feel. Useful for first impressions, not a substitute for an eval.
Win rate
From pairwise judging: how often one model's answer beat the other's.
