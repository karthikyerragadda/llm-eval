What is actually happening when an AI writes an answer?

Step 0 · 3 minutes

What you will learn, and the one idea to hold on to

If you remember a single sentence from this guide, make it this one: a large language model is a very well-read text predictor.

A large language model (LLM) is a computer program that reads some text and guesses what text should come next. That is the whole trick. Everything you have seen an AI assistant do, from writing emails to explaining code to translating a menu, is that one trick repeated many times, one small piece of text at a time.

"Large" refers to two things: the model was built from an enormous amount of text (a large part of the public internet, books, code), and the model itself is enormous (billions of adjustable numbers inside it). "Language model" is an older term from research that simply means "a program that assigns likelihoods to sequences of words".

Analogy

Picture a person who has spent years reading almost everything ever written, but who practised only one game: cover the next word and guess it. They became astonishingly good at the game. Today, when you ask them a question, they do not look anything up. They "guess the next word" of a helpful answer, over and over, until the answer is finished. They sound fluent and confident, because fluent, confident text is what they read the most. Whether the answer is true is a separate question, and it is the subject of Step 7.

Key idea

An LLM does not store facts in a database and look them up. It produces the most plausible continuation of the text it was given. Almost every strength (fluency, flexibility, breadth) and almost every weakness (making things up, forgetting long chats, bad arithmetic) follows from that single fact.

Step 1 · Text becomes numbers

Tokens: the pieces a model actually reads

Models do not see letters or words. They see tokens. This one detail explains pricing, speed limits and some famously silly mistakes.

Computers work with numbers, not letters. So before a model can read your question, a small separate program called the tokenizer chops the text into pieces and replaces each piece with an ID number. Each piece is a token. The full list of pieces the tokenizer knows is called the vocabulary. Typical vocabularies have tens of thousands to a couple of hundred thousand entries.

A token is not quite a word. Common short words ("the", "is", "Paris") are usually one token each. Longer or rarer words are split into several: "unbelievably" might become "un", "believ", "ably". Punctuation marks are usually their own tokens, and the space before a word is normally glued to the token that follows it.

Top: one sentence becomes ten tokens, each with an ID number. Bottom: a word the model sees as three chunks, which is why counting letters inside a word is a weak spot. The ␣ symbol marks a space glued to the token.

Why tokens matter to you

1Cost

Hosted models charge per token, both for what you send and for what comes back. Shorter prompts are cheaper.

2Limits

The context window (Step 3) is measured in tokens, not pages. A long document may not fit.

3Speed

The model produces one token at a time. A 300-token answer takes roughly three times as long as a 100-token one.

4Odd mistakes

Counting letters, reversing words, or rhyming can be hard because the model never sees individual letters.

Tokenizers are usually built from mostly English text, so English is "cheap". Other languages often need more tokens for the same meaning: a sentence in German, Hindi or Japanese may cost one and a half to three times as many tokens as its English translation. Code is also token-hungry, because indentation, brackets and unusual names each take pieces. Numbers are often split into small digit groups, which is one reason arithmetic is hard for a model (Step 8).

Common doubt

"If the model sees numbers, how does it understand meaning?" The ID is only a lookup key. Inside the model each ID is swapped for a long list of numbers called an embedding (Step 4), and it is those numbers that carry meaning, learned during training. The tokenizer is just the doorman that turns text into keys.

Key idea

Everything about a model is measured in tokens: what it can read at once, what it costs, how fast it answers. When you think "words", translate to "tokens, roughly a third more".

Step 2 · The core loop

Predicting the next token, again and again

A whole answer is built one token at a time. Watch the loop, then you will understand why the same question can get two different answers.

Here is the entire process of writing an answer, with nothing hidden:

  1. Take all the text so far (your question plus whatever the model has already written).
  2. Run it through the model. The model outputs a score for every token in its vocabulary, saying how likely each one is to come next. Turned into percentages, these scores are a probability distribution: a list that adds up to 100%.
  3. Pick one token from that list. Picking is called sampling. Usually the most likely token is chosen most often, but not always.
  4. Append the chosen token to the text.
  5. Go back to step 1, unless the chosen token was a special stop token (an invisible token that means "the answer is finished") or a length limit was hit.

Running a trained model to get answers like this is called inference, as opposed to training, which is how the model was built (Step 5).

The orange dot is one trip around the loop. The text so far goes in, a full list of probabilities comes out, one token is chosen and added, and the longer text goes back in. It stops when the model emits a stop token or hits a length limit.

Analogy

Think of a very fast game of "one word each". You start a story with a sentence. The model adds one piece, then reads the whole story again from the top, adds one more piece, and so on. It never plans the ending in advance. Each piece is chosen only from what is already on the page. That is why the model can start a sentence confidently and paint itself into a corner by the end of it.

Why the same question can produce different answers

Step 3 of the loop is a dice roll weighted by the probabilities. If "Paris" has 91% and "a" has 4%, then about four times in a hundred the model will write "a" and continue with something like "a city called Paris". Both are reasonable. But every token chosen changes the text so far, which changes all the probabilities that follow. Two runs that differ at token 5 can end up very different by token 50.

Applications can turn this randomness down or off (Step 6). Even at the lowest setting, small differences in the software running the model can still cause occasional variation, so never assume perfectly identical output.

Common doubt

"Does the model think about the whole answer before it starts typing?" Not in the ordinary version of the loop. The plan, if any, exists only in the form of "which next token is most likely given a text that looks like it is heading somewhere sensible". So-called reasoning models (Step 9) change this a little: they are trained to write out a draft of their thinking as ordinary tokens before the final answer, which gives them somewhere to plan.

Key idea

One token per loop, picked from a probability list, appended, repeat. Everything else in this guide is either a detail of one step in this loop or a consequence of it.

Step 3 · Working memory

The context window: everything the model can see right now

A model has no memory except the text in front of it, and that text has a hard size limit. This explains why long chats "forget" and why big documents cost more.

The context window (or just "context") is the maximum number of tokens the model can take in at once. Everything the model can use to write its next token must fit inside it:

  • The system prompt: hidden instructions the application writes, such as "You are a support assistant for a cooking app. Be brief."
  • The conversation so far: every message from the user and every earlier answer from the model.
  • Any documents, search results or tool outputs the application pasted in.
  • The answer the model is currently writing, token by token.

Everything else, including your chat from last week, the file you did not paste, and the whole internet, is invisible to it. A chat app that seems to "remember" you is quietly re-sending the earlier messages inside the window every time, or storing notes about you and pasting them in.

System prompt (from the app)You are a helpful assistant for a recipe app. Answer in under 80 words.
UserI have eggs, spinach and feta. Dinner ideas?
Assistant (earlier turn)A spinach and feta omelette takes ten minutes...
UserCan I make that without dairy?
Assistant (being written now)Yes. Swap the feta for...

All five blocks above are sent together as one long text on every turn. The model reads the whole thing from the top and predicts the next token of the last block.

The dashed blue box is the context window; its size never changes. As the conversation grows it fills up, and eventually the oldest messages are pushed out (red). The model is not "forgetting" in a human sense: those tokens were simply not sent to it.

What happens when it is full

Two things can happen, and the application decides which. Either the request is rejected with an error ("too many tokens"), or the app trims the oldest messages, or replaces them with a short summary, before sending. Neither option is free: the first breaks the conversation, the second loses detail. Good products do the trimming carefully and keep the system prompt and the most recent turns.

Analogy

Imagine a brilliant colleague who has a whiteboard of fixed size and no other memory. Whatever is on the whiteboard, they can reason about superbly. Whatever you wiped off to make room is gone, even if you wrote it yourself an hour ago. Every time you ask something, they re-read the entire board before answering, so a full board also means a slower answer.

Watch out

A bigger window is not a magic fix. Models tend to pay less reliable attention to material buried in the middle of a very long context, and every extra token you send costs money and time on every single turn. Sending only what is relevant is a core skill, and it is what the RAG guide (Part 3) is about.

Key idea

The context window is the model's entire working memory. Cost and latency scale with how much you put in it. If a fact is not in the window, the model cannot use it, no matter how many times you told it before.

Step 4 · Under the hood, gently

Inside the model: dials, layers and attention

You do not need maths to understand what the "model" box in Step 2 contains. Four ideas are enough: parameters, layers, attention and embeddings.

A neural network is a pile of tunable dials

The model is a neural network: a very large arithmetic formula that takes numbers in (the token IDs, converted to numbers) and produces numbers out (a score for each possible next token). The formula contains an enormous number of adjustable values called parameters, also called weights. Think of them as dials. "A 7-billion-parameter model" means a formula with seven billion dials. Nobody sets the dials by hand; training (Step 5) nudges them millions of times until the formula predicts text well.

The formula is organised in layers. Each layer takes the output of the previous layer and transforms it a little. Early layers tend to capture simple things (spelling, word parts); later layers capture more abstract things (grammar, topic, tone, what the question is really asking). A large model may have dozens of layers.

Analogy

A mixing desk in a recording studio has hundreds of sliders. Nobody understands what each slider does on its own, but a skilled engineer can adjust them all together until the sound is right. A language model is a mixing desk with billions of sliders, and "the sound being right" means "predicting the next token well". Training is the slow process of nudging every slider a tiny bit, over and over.

The transformer and attention

Almost all modern LLMs use a network design called the transformer. Its signature ingredient is attention. Older designs read text strictly left to right and tended to lose track of earlier words. Attention lets every token in the context look at every other token and decide which ones matter for understanding it. When processing the word "it", attention can look back and give most of its weight to "the cat", a little to "the mat", and almost none to "on".

Attention drawn as lines from "it" back to the words it is looking at. Line thickness stands for weight. Nothing here is a fixed rule; the weights are computed fresh for every sentence from the trained parameters.

Because attention connects everything to everything, its cost grows quickly with the length of the context: doubling the number of tokens roughly quadruples the attention work in the simplest version. That is one reason very long contexts are slow and expensive, and why researchers spend so much effort on cheaper variants.

Embeddings: a point in meaning-space

The first thing a model does with a token ID is swap it for an embedding: a list of a few hundred to a few thousand numbers that you can picture as coordinates of a point in a huge space. Tokens with similar meanings end up near each other. "Kitten" is near "cat", "Paris" is near "Lyon", and the direction from "king" to "queen" is similar to the direction from "man" to "woman". The layers above then push these points around until the final position encodes "what token should come next". Embeddings are also useful on their own, for search: that is the heart of the RAG guide (Part 3), which goes much deeper.

Common doubt

"So does anyone know what each parameter does?" Mostly no. The parameters were set by an automatic process, and their meaning is spread across millions of them at once. A research field called interpretability is slowly finding recognisable patterns inside models, but for everyday work you should treat the model as a black box that you test from the outside. That is why evals (Part 5) matter so much.

Key idea

Inside the box: token IDs become embeddings, dozens of layers transform them, attention lets every token consult every other token, and billions of trained parameters decide how. The output is one score per vocabulary entry. No maths is needed to use this picture, only to build it.

Go deeper: a few honest hardware facts

Running billions of multiplications per token is heavy work, so models run on GPUs (graphics processing units), chips originally built for video games that are very good at doing many multiplications in parallel. A model's parameters must sit in the GPU's memory while it runs; a model with tens of billions of parameters needs tens of gigabytes of memory, which is why the largest models are served from data centres rather than laptops. Two speed words you will hear: latency is how long you wait for a response (or for the first token), and throughput is how many tokens per second a system produces across all users. Small models win on both; large models win on quality.

Step 5 · Where the behaviour comes from

How a model is trained: three stages

A raw text predictor is not an assistant. Three training stages turn one into the other. Knowing them explains why models behave the way they do.

The green dot is the model itself moving through the three stages. Each stage starts from the parameters the previous stage produced and adjusts them further. Time and hardware figures are rough orders of magnitude, not measurements.

Stage 1: pre-training

Pre-training is the expensive part. The model starts with random parameters and is shown an enormous quantity of text, a few thousand tokens at a time. For every position it guesses the next token, is told the real one, and its parameters are nudged a tiny amount toward guessing better. Repeat this trillions of times and the model has absorbed spelling, grammar, facts, styles, code, and a great deal of the structure of human knowledge, purely as a by-product of getting good at guessing. Everything it will ever "know" about the world, it learns here. The text it saw is called its training data, and the point in time where that text ends is its knowledge cutoff (Step 8).

The result is a base model. A base model is a pure continuer. Ask it "What is the capital of France?" and it may well answer "What is the capital of Germany? What is the capital of Spain?" because a list of quiz questions is a very plausible continuation of one quiz question. It is powerful but hard to use.

Stage 2: supervised fine-tuning (instruction tuning)

Fine-tuning means continuing to train an existing model on a smaller, chosen dataset. In this stage the dataset is thousands of example conversations written or approved by people: a question, then an ideal answer. This is instruction tuning (also called supervised fine-tuning, because humans supervised the examples). The model learns the format of being an assistant: when it sees a question, it should answer it, not continue the quiz. It also learns to stop when the answer is finished, by emitting the stop token that the examples end with.

Stage 3: preference tuning (RLHF and relatives)

Writing perfect example answers is slow. Comparing two answers is fast. In preference tuning, the model writes several answers to the same question, humans (or, increasingly, another model following written rules) mark which one is better, and the model's parameters are nudged toward the preferred style: more helpful, more honest about uncertainty, less harmful, better formatted. The best-known method is RLHF, reinforcement learning from human feedback, where "reinforcement learning" simply means learning from a reward signal rather than from copied examples. Newer methods do the same job with simpler maths. The output is the polished chat model you actually talk to.

Analogy

Stage 1 is a student who reads every book in an enormous library with no teacher, and comes out knowing a huge amount but with no idea how to hold a conversation. Stage 2 is an apprenticeship: they sit beside an expert and copy how the expert answers customers. Stage 3 is customer feedback: they answer real questions, customers rate them, and they gradually adjust their manner to what people actually like.

Common doubt

"Does the model keep learning from my conversations?" Not while you chat. Inference does not change the parameters. Everything the model learned happened in training, which finished before you arrived. Providers may later use conversation data to train the next version, subject to their policies, but the model you are talking to right now is frozen.

Key idea

Knowledge comes from pre-training. Manners come from fine-tuning and preference tuning. When a model knows a fact but presents it badly, or presents a wrong fact beautifully, you are seeing those two layers separately. Fine-tuning your own model (Part 6) works on the second layer far more easily than the first.

Step 6 · The knobs

Controlling randomness: temperature, top-p, max tokens, stop sequences

Step 2 said the model rolls weighted dice. Here are the four settings that shape the dice, with a playground so you can feel what each one does.

When an application calls a model it can pass a handful of sampling settings alongside the prompt. They do not change the model's knowledge. They change how the probability list from Step 2 is turned into a single chosen token.

1Temperature

A number, usually between 0 and 2, that reshapes the probabilities. Low temperature sharpens them (the favourite token wins almost every time). High temperature flattens them (unlikely tokens get a real chance). At 0 the model always takes the single most likely token, which is called greedy decoding.

2Top-p

Also called nucleus sampling. Keep only the most likely tokens whose probabilities add up to p (say 0.9), throw away the long tail, then sample from what is left. It stops rare nonsense tokens from ever being picked, even at high temperature.

3Max tokens

A hard ceiling on how many tokens the answer may contain. When it is hit the answer is cut off mid-sentence. It protects your budget; it does not make the model write concisely.

4Stop sequences

Strings that end the answer the moment they appear, such as a newline or the word "User:". Useful when you want exactly one line, or one item from a list.

Playground 2

Temperature slider

The text so far is The capital of France is. Below are six candidate next tokens with fixed raw scores from an imaginary model. Move the temperature slider and watch the probabilities reshape. Then use top-p to cut off the tail, and press the button to roll the dice.

The raw scores are divided by the temperature and then turned into percentages (the formula is called softmax). Grey bars are candidates that top-p has removed: they can never be sampled, whatever their probability was.

What you should have seen

  • Low temperature (0.1 to 0.3): one bar dominates. The output is predictable and repetitive. Good for extraction, classification, code, anything with one right answer.
  • Temperature around 1: the raw scores are used as they are. This is the natural setting the model was trained toward, and a common default for chat.
  • High temperature (1.5 to 2): bars flatten and "Lyon" or "lovely" get picked regularly. Creative, surprising, and increasingly incoherent.
  • Top-p: at 0.9 the rarest candidates are cut. At 1.0 nothing is cut. Lowering it is a safety net against nonsense without making the output as rigid as low temperature does.
Analogy

Temperature is the mood of a chef choosing tonight's special. At low temperature they cook the dish they know sells best, every night. At high temperature they are willing to try the odd combinations at the back of the recipe book. Top-p is the manager removing the truly bizarre recipes from the book before the chef even starts, so that however adventurous the chef feels, nobody gets served ice cream soup.

The same settings in code

Every provider's library exposes these settings under similar names. The function call_model below stands in for whichever one you use.

# One call to a language model, with the four sampling controls from this chapter.
# call_model() stands for whatever provider library you use; the ideas are the same everywhere.

def answer(question):
    prompt = "Answer in one short paragraph.\n\nQuestion: " + question + "\nAnswer:"
    reply = call_model(
        prompt,
        temperature=0.2,            # low: mostly the most likely tokens, few surprises
        top_p=0.9,                  # drop the rare tail before sampling
        max_tokens=200,             # hard cap on answer length (protects the budget)
        stop=["\nQuestion:"],       # stop if the model starts inventing a new question
    )
    return reply.strip()

print(answer("Why does bread rise?"))
Common doubt

"Should I just always use temperature 0 to get the right answer?" Temperature 0 gives the most likely answer, not the most correct one. If the model's best guess is wrong, it will be wrong every time, just consistently. Low temperature is about repeatability, which is valuable for testing and for structured output. It is not a truth setting.

Practical tip

Change one knob at a time and start from the defaults. For anything you will evaluate automatically (Part 5), fix the temperature low so that runs are comparable. For brainstorming, raise it. Set max tokens generously and control length with instructions in the prompt instead, so that answers are not chopped mid-sentence.

Key idea

Sampling settings shape how the dice are rolled, nothing more. Temperature sharpens or flattens the odds, top-p removes the long tail, max tokens and stop sequences decide when to stop rolling.

Step 7 · The famous failure

Hallucination: confidently wrong

Why a fluent predictor sometimes states false things with total confidence, when it gets worse, and the defences that actually work.

A hallucination is a fluent, plausible statement produced by the model that is simply not true: a book that does not exist, a legal case that was never filed, a function that is not in the library, a statistic with the wrong number. The name is a bit dramatic; "confident guess" is closer to the truth.

Given everything so far, the cause is not mysterious. The model's job is to produce the most plausible next token. If you ask for the title of a paper by a particular author, then a plausible-looking title is exactly what the loop will produce, whether or not such a paper exists. Nothing in the loop checks against reality. There is no database lookup step, and there is no separate "do I actually know this?" step. The model's confidence comes from its fluency, and its fluency is the same whether it is right or wrong.

Analogy

Think of a charming dinner guest who has read widely and hates saying "I don't know". Ask them about a village they have never visited and they will describe its charming church and Tuesday market with perfect assurance, because that is what villages are usually like. They are not lying; they are pattern-completing. The pattern is usually right, which is exactly what makes the wrong cases dangerous.

When it gets worse

Obscure facts

The rarer a topic was in the training data, the weaker the model's actual knowledge and the more it fills gaps with the typical pattern.

Citations and quotes

Titles, authors, URLs and page numbers have a very regular shape, so inventing a convincing one is easy. Verify every reference.

Numbers

Digits are tokens like any other. A plausible-looking figure is often preferred over the exact one, especially in long tables.

Recent events

Anything after the knowledge cutoff (Step 8) is a guess dressed as a fact, unless the app supplies the information.

Leading questions

"Why did X cause Y?" invites an explanation even when X did not cause Y. The premise is accepted because agreeing is the fluent continuation.

Long answers

Each token is a small gamble. The more tokens, the more chances for one wrong turn that the rest of the answer then builds on.

Defences that work

  1. Put the source in the window. If the answer must come from a document, paste the document (or the relevant parts) into the context. The model is far more reliable when it is reading than when it is recalling. Doing this automatically at scale is retrieval-augmented generation, RAG, the subject of Part 3.
  2. Ask for citations to the provided text. "Quote the sentence you used" makes fabrication harder and makes checking easier.
  3. Allow "I don't know". Tell the model explicitly that saying it cannot find the answer is acceptable. Preference tuning makes models eager to please; permission to decline counteracts it.
  4. Verify with tools. Let the model call a calculator, a search engine or a database rather than guess (Part 4).
  5. Measure it. Build a set of questions with known answers and check the failure rate every time you change something. That is an eval (Part 5), and hallucination rate is one of the most common things to measure.
Watch out

Asking the model "Are you sure?" is a weak check. The model answers with the most plausible response to being asked whether it is sure, which is often "Yes, I am sure" or an equally confident correction that is also wrong. Verification has to come from outside the model: a document, a tool, a test, or a human.

Common doubt

"Will bigger models fix hallucination?" Larger and better-trained models hallucinate less, and preference tuning can teach a model to hedge more often. But as long as the core mechanism is "produce the most plausible continuation" with no built-in check against the world, the rate cannot reach zero. Plan your product around the failure being possible.

Key idea

Hallucination is not a bug in an otherwise fact-checking system. It is the normal behaviour of a text predictor when the plausible continuation happens to be false. Reduce it by giving the model the facts, permission to abstain, tools to check, and by measuring the rate.

Step 8 · Honest limits

What a model cannot do on its own

A short list of built-in limits. Every one of them can be worked around by the application, and later guides show how, but the raw model has none of these abilities.

No knowledge after its knowledge cutoffAll knowledge came from pre-training text, which ended on a date (Step 5).Paste in fresh information, or give it a search tool (Parts 3 and 4).
No memory between conversationsParameters are frozen; only the context window exists (Steps 3, 5).The app stores notes and re-inserts them into the window.
Unreliable arithmeticDigits are tokens; it predicts plausible digits, it does not calculate (Step 1).Give it a calculator or code tool and ask it to use it (Part 4).

None of this makes the model useless. It means the model is one component. Around it sits an application that decides what goes in the window, watches what comes out, runs tools when asked, stores memory, and checks results. Most of the work of "building with LLMs" is building that surrounding application well.

Analogy

A brilliant new colleague arrives who has read everything up to a certain date, has no phone, no computer, no calendar and no memory of yesterday, and can only communicate through notes passed under the door. You would not fire them. You would build a workflow around them: put the right papers under the door, give them a calculator, write down what they said yesterday, and check the numbers before sending anything to a customer. That workflow is the rest of this series.

Common doubt

"But the chat app I use does browse the web and remember me." Yes, the app does. It uses tools (Part 4) to fetch pages and pastes the results into the window, and it keeps a memory store that it re-inserts. The underlying model still only predicts tokens. Knowing where the model ends and the app begins helps you understand which failures are which.

Key idea

The raw model reads a window of tokens and writes tokens. Everything else, from memory to browsing to arithmetic, is added by the software around it. When a product "can" or "cannot" do something, ask which layer is responsible.

Step 9 · Choosing

The model landscape: size, openness, reasoning, modality

You will hear a lot of model names. Ignore them for now and learn the four axes along which models really differ.

Size: quality versus speed versus cost

Model size is counted in parameters. As a loose rule, more parameters means better quality: more nuance, more knowledge, fewer mistakes on hard tasks. The price is that every token requires more arithmetic, so large models are slower per token, need bigger and more expensive hardware, and cost more to run. Small models answer quickly and cheaply and are perfectly good at simple, well-defined jobs such as classifying a support ticket or extracting a date from an email.

The trade-off in one picture. Bigger models are better and slower and dearer, all at once. The skill is matching the model to the difficulty of the job, not always buying the largest.

Open-weight versus hosted API

An open-weight model is one whose parameter file has been published. Anyone can download it and run it on their own hardware, fine-tune it, or inspect it. A hosted API model runs on the provider's servers; you send text over the internet and receive text back, paying per token, and you never see the parameters. Hosted models are usually the largest and most capable and require no hardware; open-weight models give you control, privacy and predictable cost, at the price of running the infrastructure yourself. Many teams use both: a hosted model for hard tasks, a small open-weight model for high-volume simple ones.

Reasoning models

A reasoning model is trained to write out intermediate steps, as ordinary tokens, before giving its final answer. Instead of answering "What is 17 times 24?" in one shot, it writes "17 times 20 is 340, 17 times 4 is 68, total 408" and then answers. The app often hides those thinking tokens from you. This helps a lot on maths, logic, planning and code, because it gives the next-token loop somewhere to work things out. The cost is real: those extra tokens take time and money. For a simple lookup or a friendly chat reply, a reasoning model is slower for no benefit.

Multimodal models

A multimodal model accepts more than text: images, sometimes audio or video, and sometimes produces them too. Under the hood the trick is the same one from Step 1: a picture is chopped into patches and each patch becomes a token-like piece, so the same loop can "read" a photo of a receipt or a diagram. Image tokens can be expensive, so a single photo may cost as much as several paragraphs of text.

Small models on your own machine

Small open-weight models can now run on an ordinary laptop or phone. They are weaker than the giants but they cost nothing per token, work offline and never send data anywhere. For a hobby project, for privacy-sensitive data, or for a narrow task like tagging notes, they are often the right choice. The Production guide (Part 8) covers the serving software that makes this practical.

Analogy

Choosing a model is like choosing transport. A bicycle (small model) is cheap, fast for short trips and needs no fuel, but you would not cross a continent on one. A jet (large hosted model) will take you anywhere but you pay per seat and follow the airline's schedule. Owning a car (open-weight model) means buying and maintaining it, but you go where you like with nobody watching. A reasoning model is the option where the driver stops to study the map first: slower to leave, less likely to get lost.

Common doubt

"Should I always pick the newest, biggest model?" Start with a capable model to find out whether the task is possible at all, then try to move to something smaller and cheaper once you have an eval (Part 5) that tells you when quality drops. Many production systems run most of their traffic on a mid-sized or small model and route only the hard cases to a large one.

Key idea

Models differ along four axes: size (quality versus speed and cost), openness (control versus convenience), reasoning (thinking tokens versus latency) and modality (text only versus images and audio). Names and version numbers change every few months; these four axes do not.

Quiz and glossary

Six quick questions to test the mental model, then every term from this guide in one place.

Glossary

Attention
The part of a transformer that lets each token look at every other token in the context and weigh how relevant each one is. It is how "it" comes to mean "the cat".
Base model
The model straight after pre-training. It continues text but does not follow instructions or behave like an assistant.
Chat model
A model that has been through instruction tuning and preference tuning, so it answers questions helpfully and stops when done.
Context window
The maximum number of tokens the model can read at once: system prompt, conversation, documents and the answer in progress. Its entire working memory.
Embedding
A list of numbers that represents a token (or a whole text) as a point in a "meaning space", where similar meanings are close together.
Fine-tuning
Continuing to train an existing model on a smaller, chosen dataset to change its behaviour or specialise it.
GPU
Graphics processing unit. A chip that does huge numbers of multiplications in parallel; the hardware models are trained and run on.
Greedy decoding
Always choosing the single most likely next token. What temperature 0 means in practice.
Hallucination
A fluent, plausible statement from the model that is not true. The normal behaviour of a text predictor when the plausible continuation is false.
Hosted API
A model that runs on the provider's servers. You send text over the internet and pay per token; you never see the parameters.
Inference
Running a trained model to get answers, as opposed to training it. The parameters do not change during inference.
Instruction tuning
Fine-tuning on example question-and-answer pairs so the model learns to follow instructions. Also called supervised fine-tuning.
Knowledge cutoff
The date after which the model's training text ends. It knows nothing later than this unless the app supplies it.
Large language model (LLM)
A very large neural network trained on huge amounts of text to predict the next token, and then tuned to be a useful assistant.
Latency
How long you wait for a response, or for the first token of it. Bigger models and longer contexts increase it.
Layer
One stage in the neural network. Each layer transforms the output of the previous one; large models have dozens.
Max tokens
A hard limit on how many tokens the model may write in one answer. When hit, the answer is cut off.
Multimodal
A model that accepts (and sometimes produces) more than text, such as images or audio, by turning them into token-like pieces.
Neural network
A large arithmetic formula with millions or billions of adjustable parameters, tuned automatically during training.
Open-weight
A model whose parameter file is published, so anyone can download, run, inspect and fine-tune it.
Parameter / weight
One adjustable number inside the model. "Seven billion parameters" means seven billion such dials, set by training.
Preference tuning
Training the model on human (or model) judgements of which of two answers is better, so it learns the style people prefer. RLHF is one method.
Pre-training
The first and most expensive training stage: predicting the next token across trillions of tokens of text. Produces the base model and all of its knowledge.
Probability distribution
A list of percentages, one per possible next token, adding up to 100%. The model's output at every step of the loop.
Prompt
The text you send to the model: your question or instruction plus any context. The subject of Part 2.
RAG
Retrieval-augmented generation: search your documents first, paste the relevant parts into the context, then let the model answer from them. Part 3.
Reasoning model
A model trained to write out intermediate thinking as tokens before its final answer. Better at maths and planning, slower and costlier.
RLHF
Reinforcement learning from human feedback. A preference-tuning method where the model learns from a reward built from human comparisons of answers.
Sampling
Choosing one next token at random, weighted by the probabilities. Temperature and top-p change how this is done.
Stop sequence / stop token
A stop sequence is a string that ends the answer as soon as the model produces it, such as a newline or "User:". The stop token is the model's own invisible "I am finished" token, learned during instruction tuning.
System prompt
Hidden instructions from the application, placed at the top of the context, that set the model's role and rules.
Temperature
A setting that sharpens (low) or flattens (high) the probabilities before sampling. Low is predictable, high is creative and riskier.
Throughput
How many tokens per second a system produces across all users. A measure of serving capacity.
Token
A piece of text, roughly three quarters of an English word, that the model reads and writes. Everything is counted in tokens.
Tokenizer
The small program that splits text into tokens and maps each one to an ID number, and back again.
Tool / tool use
Letting the model request an action (search, calculator, code) in a special format that the app carries out and reports back. Part 4.
Top-p
Nucleus sampling: keep only the most likely tokens whose probabilities add up to p, discard the rest, then sample.
Training data
The text a model learned from during pre-training. Its knowledge, style and biases all come from here.
Transformer
The neural network design used by almost all modern LLMs, built around attention layers.
Vocabulary
The fixed list of all tokens a tokenizer knows, typically tens of thousands to a couple of hundred thousand entries.
